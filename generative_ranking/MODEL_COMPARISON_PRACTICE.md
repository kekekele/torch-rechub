# 同一数据集下三类排序模型的实战对比：DCNv2、OneTrans 与 RankMixer

## 1. 背景

在排序任务里，模型对比最容易做成“只报一个最终指标”的实验记录，但真实项目里更重要的问题通常是另外几个：模型是否稳定、是否容易复现、是否值得继续投入。本次总结围绕 `generative_ranking` 当前已经实现的三类模型展开，目标不是做一次孤立的跑分，而是沉淀一套更适合后续重复使用的比较方法。

结合当前工程实现，这次对比有两个比较好的前提：一是训练入口、推理入口和数据协议已经统一，二是 `DCNv2`、`OneTrans` 和 `RankMixer` 三类模型已经都能在同一套数据准备流程下运行。因此，这篇文章更适合写成“同一实验基座上的三类模型实战比较”，而不是单模型复现记录。

## 2. 模型对象

这次选的三个模型，对应的是三种明显不同的排序建模路线。

### 2.1 DCNv2

`DCNv2` 更像是经典特征交互路线的代表。在当前实现里，它直接使用 `bundle["dcn_v2_features"]`，把 embedding 展平后的特征向量送入 cross network 和 MLP 结构，重点利用显式特征交叉能力来完成 CTR 预测。

如果把它放到这次对比里看，它最适合承担两个角色：

- 作为稳定基线，帮助判断数据和特征体系本身是否已经具备足够信息量
- 作为对照项，衡量更复杂结构是否真的带来了额外收益

当前默认配置下，`DCNv2` 使用：

- `n_cross_layers = 3`
- `mlp_params.dims = [256, 128]`
- `mlp_params.dropout = 0.2`
- `mlp_params.activation = relu`

### 2.2 OneTrans

`OneTrans` 更偏序列建模路线。在当前实现里，它同时接收统一特征集合和历史序列特征，通过 `sequence_features` 构造真实序列 token，再结合 `ns_len` 个非序列 token 做混合建模。它更关注行为顺序、历史依赖以及序列与非序列信息的联合表达。

在这次对比里，`OneTrans` 更适合回答的问题是：如果数据里确实存在较强的时序信号，那么引入更明确的序列建模之后，是否能稳定超过经典交互模型。

当前默认配置下，`OneTrans` 使用：

- `d_model = 128`
- `ns_len = 4`
- `num_heads = 4`
- `ffn_hidden = 256`
- `multi_num = 2`
- `num_pyramid_layers = 4`
- `pyramid_align = 1`
- `mask_type = paper_causal`
- `use_sep_token = false`

### 2.3 RankMixer

`RankMixer` 代表的是统一表达与多类型特征融合路线。在当前实现里，它同样使用统一特征集合和序列特征，但不是直接做标准自注意力，而是先把不同类型输入映射到统一语义空间，再做语义 token 化、token mixing 和 per-token 变换。

它更适合回答的问题不是“序列是否重要”，而是“多种输入信息是否值得先压到统一表达里，再做更深层的交互”。如果后续你想把文章落到建模思路层面，`RankMixer` 这一节可以重点写它如何处理多类型输入，而不是展开实现细节。

当前默认配置下，`RankMixer` 使用：

- `d_model = 128`
- `num_layers = 2`
- `num_tokens = 4`
- `seq_pool_modes = ["mean", "target"]`
- `use_moe = true`
- `moe_experts = 4`
- `moe_l1_coef = 0.0001`
- `moe_sparsity_ratio = 0.5`
- `moe_use_dtsi = true`
- `moe_routing_type = relu_dtsi`

## 3. 实验设计

为了让后面的结果更有说服力，这次对比应当尽量把模型之外的变量收紧。当前工程已经提供了比较好的基础：统一的配置目录、统一的数据协议、统一的训练入口和统一的评估函数。因此，这一节最重要的任务是说明“这次实验如何做到基本公平”。

### 3.1 数据与任务

当前内置配置使用的是 `MovieLens-1M`，配置目录位于 `generative_ranking/config/movielens/`。从当前 `data.json` 看，数据准备采用统一三表协议：

- `seq.csv`：交互表，当前保留 `uid`、`iid`、`timestamp`、`label`
- `user_info.csv`：用户表，当前保留 `uid`、`gender`、`age`、`occupation`、`zip_code`
- `item_fea.csv`：物品表，当前保留 `iid`、`title`、`genres`

这三张表通过 `uid` 和 `iid` merge 成统一交互表，再进入样本构造流程。当前样本构造的关键设置包括：

- `user_id_col = uid`
- `timestamp_col = timestamp`
- `label_col = label`
- `max_seq_len = 101`
- `history_filter.positive_only = true`
- `split.type = global_time_ratio`
- `split.ratios = [0.8, 0.1, 0.1]`

也就是说，当前默认流程更适合写成：在统一时间排序和统一切分规则下，对三类模型做同数据源比较。

当前 `movielens/data.json` 中已经明确了统一特征口径，可直接作为文章里的实验说明：

## 5. 结果分析

这一节不建议写成“逐个解释某个指标为什么高一点”，而更适合从三类模型各自依赖什么信息、又更受什么条件约束来分析。

### 5.1 哪类模型更稳

如果后续结果显示 `DCNv2` 的验证曲线更平稳，这通常不意外。它在当前工程里走的是更直接的特征交互路线，输入组织和训练目标都更简单，因此更适合承担“稳定参照系”的角色。

### 5.2 哪类模型更依赖序列质量

如果 `OneTrans` 的收益明显依赖样本中的序列信息，这同样是合理的。当前数据构造里已经明确了 `timestamp`、`max_seq_len = 101` 和 `positive_only` 的历史过滤方式，因此后续若要解释它的表现，应重点结合序列长度、历史质量和时序信号来写，而不是只看模型结构本身。

### 5.3 哪类模型更依赖特征组织

`RankMixer` 更值得结合统一输入表达来分析。当前语义分组里已经显式区分了 `user_profile`、`target_item`、`sequence_global`、`sequence_target`，这意味着它是否能跑出优势，往往取决于这些输入分组是否真的形成互补，而不只是网络是否更复杂。

### 5.4 为什么更复杂不一定更优

这部分建议写得更像经验判断：

- 如果额外表达能力没有对应的信息支撑，复杂模型很难稳定兑现收益
- 如果收益很小但训练成本明显增加，复杂度未必值得
- 在统一实验基座上，真正值得继续投入的模型，通常不是“偶尔最好”的那个，而是“稳定更优”或者“明显打开上限”的那个

## 6. 经验与建议

这一节建议把前面的实验结果翻译成真正可执行的选型建议。

### 6.1 什么时候先用 DCNv2

如果当前目标是建立一个可信基线、先验证数据协议是否正确、或者先看统一特征在经典交互模型上的表现，那么 `DCNv2` 仍然是最合适的起点。它在当前工程里结构最直接，也最容易作为后续比较的参照系。

### 6.2 什么时候重点看 OneTrans

如果你更关心用户历史行为顺序是否提供了额外信息，或者希望验证时序关系在当前任务里是否真的重要，那么 `OneTrans` 更值得重点观察。它不一定总是最优，但它能更直接地回答“序列建模是否有必要继续投入”。

### 6.3 什么时候尝试 RankMixer

如果数据中混合了多类型输入，希望进一步验证统一表达和 token 级交互是否带来收益，那么 `RankMixer` 更值得继续做。尤其是在当前工程已经定义了 `semantic_schema` 的前提下，它天然适合被写成“特征组织方式是否影响模型上限”的代表模型。

### 6.4 选型时真正该看什么

在真实项目里，最不值得做的事情，就是因为某个模型在一轮实验里分数最高，就直接把它当成最终方案。更好的判断方式通常是：

- 先看哪个模型最容易稳定复现
- 再看哪个模型在合理成本下持续领先
- 最后再决定是否值得继续为更复杂结构投入时间

## 7. 总结

如果把这次文章的重点压缩成一句话，那么最值得强调的并不是“哪一个模型一定更强”，而是：在统一实验基座下比较三类模型，能够更清楚地看到它们各自适合解决什么问题，又分别依赖什么数据条件。

- 数据协议统一，适合写“公平对比”的方法部分

- 训练和评估入口统一，适合补充一套后续可复用的实验模板
