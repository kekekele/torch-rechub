# 大模型使能交付实战系列：基于 RecKit 的推荐排序模型工程实践

## 1. 引言

本文是“大模型使能交付实战系列”中的推荐排序篇，核心关注点不是单一模型介绍，而是基于团队自建资产包 RecKit，梳理推荐排序模型的工程实现方式、实验组织方法以及面向项目场景的复用思路。

在推荐排序相关工作中，真正影响交付效率的往往不只是模型本身，还包括数据入口是否统一、训练流程是否可复用、评估口径是否一致、不同模型是否便于横向比较。围绕这些问题，我们建设了 RecKit 这一资产包，用来承接从原始数据预处理、模型训练、离线评估到实验对比的完整过程。

在此基础上，本文以三个排序模型为主线展开：

- DCNv2
- RankMixer
- OneTrans

同时结合两个典型数据场景说明这套实现如何支撑实验分析：

- AmazonElectronics_x1：特征相对较少，结构较轻。
- TaobaoAd_x1：特征更丰富，时间依赖更强，更接近真实广告排序场景。

本文希望说明的是，RecKit 不只是一个代码仓库，而是一套面向推荐排序交付的工程资产；围绕这套资产，我们已经具备了组织多模型实现、统一实验流程并支撑后续项目方案设计的能力。

## 2. 为什么要建设 RecKit 这样的资产包

### 2.1 推荐排序交付中的共性问题

在实际交付过程中，推荐排序往往会遇到几类共性问题：

- 不同项目的数据来源和字段命名方式不统一，导致模型切换成本高。
- 同一类任务在不同模型下往往重复开发数据处理、训练和评估逻辑。
- 实验结果容易受到切分策略、特征口径、实现细节差异的影响，难以横向比较。
- 即使模型效果不错，如果缺少统一工程承载，也难以沉淀成可复用能力。

如果每个项目都从零开始搭建训练脚本和数据流程，不仅交付效率低，而且很难形成稳定的模型选型方法论。

### 2.2 RecKit 的资产化价值

RecKit 的建设目标，就是把推荐实验中真正可复用的部分沉淀下来，把重复工作变成统一资产。它的核心价值主要体现在三个方面：

- 统一原始数据入口，降低不同项目和不同模型之间的数据切换成本。
- 统一训练、推理、评估的基本流程，降低重复开发成本。
- 为多模型对比实验提供一致的工程底座，便于沉淀模型选型和场景判断能力。

因此，本文的重点不是单独解释某个模型，而是说明资产包如何承接模型实现和实验组织，最终形成面向项目的工程实践能力。

## 3. RecKit 如何支撑推荐排序实现

### 3.1 统一数据入口与流程组织

从仓库设计上看，RecKit 的基本思路是统一原始数据入口，但允许不同方法保留自己的数据构造、训练目标和推理方式。整体流程可以概括为：

```text
统一原始数据
  -> 方法本地预处理
  -> 训练样本 / 索引 / SID / prompt
  -> 模型训练
  -> 推理或生成
  -> 指标评估
```

这种组织方式的好处在于，数据规范和实验流程可以统一，但具体模型不需要被强行抽象成同一种结构。对于排序任务而言，这一点尤其重要，因为显式特征交叉模型、token 交互模型和序列 Transformer 模型对输入形式的要求差异很大。

### 3.2 模型本地化实现与公共能力分层

RecKit 将真正通用的能力沉淀在公共层，例如数据处理、基础工具和通用评估；方法自身的预处理、dataset、模型结构、训练逻辑、推理逻辑和配置则尽量放在方法目录内。这样的分层带来两点价值：

- 一方面，模型可以保留自身最合适的实现方式，不被公共抽象限制。
- 另一方面，公共部分又能保证不同模型在实验组织上保持一致。

这使得 RecKit 很适合作为排序资产包来承接多模型实现。

### 3.3 项目级实验组织方式

在具体项目目录中，RecKit 支持以数据集或业务主题为单位组织实验。例如当前的 TaobaoAd_x1 项目目录中，DCNv2、RankMixer 和 OneTrans 各自维护配置，同时由统一脚本组织单次运行和 K-fold 对比。这样既能保持模型差异，又能把实验结果放在同一工程上下文里理解。

从工程实践角度看，这种结构有助于回答三个问题：

- 同一个数据场景下，不同模型如何保持同口径对比。
- 同一个模型在不同数据场景下，如何快速复用实现。
- 后续项目进入方案设计时，如何基于现有资产快速搭建 PoC 或实验验证。

## 4. 基于 RecKit 的三类排序模型实现

### 4.1 DCNv2：显式特征交叉实现

DCNv2 是面向 CTR/ranking 的特征交叉模型。在 RecKit 中，它的实现方式是先将用户、目标物品、上下文和历史等特征编码成一个扁平向量，再通过 CrossNet 显式建模高阶特征交叉，并使用 MLP 补充隐式非线性表达。

当前实现支持两类交叉网络：

- 标准 CrossNetV2
- low-rank mixture cross network

其中，low-rank mixture cross network 通过低秩参数与专家门控降低交叉层参数量，同时保留多专家表达能力。模型还支持 `parallel`、`stacked` 和 `crossnet_only` 等组合结构，用于适配不同实验配置。

从工程视角看，DCNv2 的特点在于：

- 对结构化特征友好。
- 不依赖显式 token 顺序。
- 作为工业基线模型实现稳定，训练和解释成本相对可控。

因此，它非常适合作为资产包中的稳定基础模型，用于承接轻特征或规则较清晰的排序场景。

### 4.2 RankMixer：语义块 token 交互实现

RankMixer 是一个面向排序任务的 block/token 模型。在 RecKit 中，它先把输入按业务语义组织成 `user`、`history`、`context`、`target` 等 feature blocks，再将各个 block 转换成固定数量的 tokens，通过多层 RankMixer block 建模 token 间交互，最后输出排序得分。

每个 RankMixer block 包含两个核心组成：

- Parameter-free token mixing：把 token 按 head 切分后跨 token 重排，实现无参数的全局交互。
- Per-token FFN / Sparse MoE：为每个 token 提供独立 FFN 表达，必要时引入稀疏专家路由。

与传统序列模型不同，RankMixer 对历史信息的处理更偏“语义摘要”而非“逐位置序列保留”。history block 会先对整段历史做 mask-aware summary，再压缩成若干语义 tokens。这样做的好处是，在字段丰富且语义边界清晰的场景下，可以更高效地表达多源特征之间的组合关系。

因此，在资产包中，RankMixer 更适合作为多特征、多语义组场景下的增强型排序实现。

### 4.3 OneTrans：序列与非序列统一建模实现

OneTrans 将推荐排序输入统一成一段 token 序列：多行为历史进入 S tokenizer，用户、目标物品和上下文等非序列特征进入 NS tokenizer。随后将 `S tokens + NS tokens` 拼接后送入因果 Transformer，并通过尾部 NS tokens 聚合完整历史证据。

在实现上，OneTrans 兼顾了两类不同信息：

- S tokens 共享 QKV/FFN 参数，用于建模行为序列的同质性。
- NS tokens 使用 token-specific QKV/FFN 参数，用于表达非序列语义组的异质性。

此外，OneTrans 通过 pyramid schedule 逐层保留尾部 query，把前面的历史信息逐步压缩到后部 tokens 上。最终输出 head 会聚合这些 NS tokens，用于 CTR/CVR 等排序预测。

从资产包能力角度看，OneTrans 提供的是一类更强的时序建模实现。对于历史行为模式复杂、时间依赖明显、且需要同时利用静态特征和行为序列的场景，它能够补充 DCNv2 和 RankMixer 的能力边界。

## 5. 基于资产包的实验组织与对比方法

### 5.1 为什么选择 AmazonElectronics_x1 与 TaobaoAd_x1

为了说明资产包如何支撑多模型实验，本文选取了两个差异明显的数据场景：

- AmazonElectronics_x1：字段较少，结构化程度高，更适合观察轻特征场景下的模型表现。
- TaobaoAd_x1：用户侧、物品侧、上下文侧和历史侧字段更丰富，更适合观察多特征和强时序场景下的模型差异。

这两个数据场景的价值不在于覆盖所有业务，而在于能够用一轻一重两类任务，把模型能力边界在统一工程框架下暴露出来。

### 5.2 轻特征场景下的实验组织

在 AmazonElectronics_x1 上，核心输入字段主要围绕 `user_id`、`item_id`、`cate_id` 以及相对简化的历史信息展开。转换为 RecKit 通用 raw 格式后，`user_info.csv` 和 `item_fea.csv` 的结构都相对克制。

这一场景更适合用来比较：

- 当输入特征不复杂时，DCNv2 这样的显式交叉模型是否已经足够。
- 更复杂的 token 交互或序列建模结构，是否能带来稳定且值得的收益。

从工程实践角度看，这类场景有助于建立“强基线优先”的实验习惯。

### 5.3 多特征与强时序场景下的实验组织

TaobaoAd_x1 的字段更丰富，用户侧包含年龄、性别、消费层级、职业、新客等级等信息，物品侧包含类目、campaign、brand、price 等信息，序列和上下文侧还包含 `pid`、`btag_his`、`cate_his`、`brand_his` 等历史字段。

这类数据场景更接近真实广告排序问题，因此实验重点不只是比较模型分数，还包括比较：

- 多语义块交互能力是否能放大特征价值。
- 时序统一建模是否能更好利用行为演化信号。
- 不同模型在更复杂数据口径下的稳定性和工程成本差异。

### 5.4 为什么采用 blocked time K-fold

TaobaoAd_x1 项目中采用 blocked time K-fold，而不是随机 K-fold，其原因在于该数据集具有更强的时间依赖。具体做法是：

- 按时间戳对样本排序。
- 将完整时间轴划分为连续的 K 个块。
- 每次选择一个块作为测试集。
- 用相邻块作为验证集。
- 其余更早和更晚的块作为训练集。

这一设计更接近真实部署环境，也能减少时间泄漏。因此，基于 RecKit 的实验组织不只是为了得到分数，更是为了让实验结论具备更高的可解释性和可复用性。

## 6. 从实验看排序模型的适用场景

### 6.1 轻特征场景下的模型选择

在轻特征场景下，如果复杂模型相对 DCNv2 的收益有限，那么更合理的工程选择往往是优先使用结构稳定、训练成本更可控的模型。此时，DCNv2 作为资产包中的强基线价值会非常突出。

### 6.2 多特征场景下的模型选择

当用户、上下文、目标物品和历史字段都更丰富时，按语义块组织 token 的 RankMixer 往往更容易放大字段价值。对于特征组丰富、语义边界清晰的场景，它能在表达能力和工程可控性之间取得较好的平衡。

### 6.3 强时序场景下的模型选择

如果问题的关键不只是字段交互，而是行为序列本身的演化模式，那么 OneTrans 的统一序列建模能力会更有价值。尤其是在时间依赖明显、历史模式复杂的场景中，简单摘要往往不足以保留关键信号，此时 OneTrans 提供了更强的时序表达能力。

### 6.4 模型选择不只看离线分数

在工程实践中，模型选择不应只由单个离线指标决定，还需要同时考虑：

- 数据准备复杂度
- 训练成本与推理成本
- 对切分策略是否敏感
- 是否容易复现稳定结果
- 后续是否便于扩展新特征和迁移到其他项目

因此，RecKit 的价值不仅在于支持多模型训练，更在于帮助团队形成“按场景选择模型”的工程方法。

## 7. 排序资产在项目场景中的复用思路

RecKit 作为排序资产包，其复用价值不局限于传统推荐排序任务。更重要的是，它提供了一套“多源信息建模 + 候选打分排序”的通用分析框架，这套框架可以迁移到更多项目场景中。

### 7.1 NPS 贬损识别

在 NPS 贬损识别问题中，可以把用户属性、触点上下文、历史交互、服务记录、文本衍生标签等信息组织成排序或判别输入：

- 当重点在于多类结构化属性之间的组合关系时，可以借鉴 DCNv2。
- 当不同信息源之间存在清晰语义分组时，可以借鉴 RankMixer。
- 当用户情绪变化或风险信号强依赖事件先后顺序时，可以借鉴 OneTrans。

从项目复用角度看，NPS 贬损识别并不只是一个简单分类问题，也可以被组织成“风险信号排序”的问题。

### 7.2 根因定界

根因定界类任务同样适合使用排序思路来组织。可以将用户症状、操作链路、时间上下文、对象属性、历史事件等组成输入特征，再把候选根因视为待排序对象：

- DCNv2 适合建模跨字段组合关系较强的场景。
- RankMixer 适合建模多语义块之间的相互作用。
- OneTrans 适合建模具有明显事件链条和时间顺序的传播过程。

这意味着，RecKit 所沉淀的不只是推荐领域的模型实现，还包括可面向其他项目场景迁移的排序分析方法。

## 8. 总结

围绕 RecKit 这一资产包，推荐排序相关能力可以从“单次项目实现”进一步沉淀为“可复用工程实践”。在这套实践中：

- DCNv2 提供稳定的显式特征交叉基线。
- RankMixer 提供面向多语义块的 token 交互能力。
- OneTrans 提供更强的时序统一建模能力。

与此同时，AmazonElectronics_x1 与 TaobaoAd_x1 这两类差异明显的数据场景，为资产包支撑多模型实验、比较模型适用边界、形成选型方法提供了良好的验证基础。

因此，这篇文章更想说明的不是某个模型绝对优于另一个模型，而是基于 RecKit 这样的资产包，团队已经能够把推荐排序模型的实现、训练、评估和实验组织成一套可复用的工程实践，并将这套能力进一步服务于后续项目场景。
